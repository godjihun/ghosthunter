# 기술 디자인 문서

게임 규칙·밸런스는 [ghost_game_scenario.md](ghost_game_scenario.md)에 있다. 이 문서는 **그 규칙을 어떤 기술로 어떻게 구현할지**를 정한다.

시나리오 문서가 "무엇을"이라면 이 문서는 "어떻게"다. 구현이 이 문서와 달라지면 문서를 갱신할 것.

---

## 제출 요건 (외부 제약)

아래는 우리가 정한 설계가 아니라 **반드시 지켜야 하는 조건**이다. 기술 선택이 이 요건과 충돌하면 요건이 이긴다.

| 요건 | 현재 대응 | 상태 |
|---|---|---|
| 웹 빌드로 배포, **링크 클릭만으로 브라우저에서 바로 플레이** | WebGL 빌드 + 정적 호스팅 (8-2) | ✅ 스택이 이미 이 전제 |
| **별도 유료 라이선스 없이 심사자가 실행** 가능 | Unity·NGO 무료, UGS는 무료 티어 내, 호스팅 무료 플랜 | ✅ 유료 요소 없음 |
| 실행 방법 문서화 | 아래 "실행 방법" | ⬜ 배포 후 채울 것 |
| 플레이 링크 제공 | 아래 "실행 방법" | ⬜ 배포 후 채울 것 |
| (자체 결정) 플레이 영상 첨부 | 심사자가 직접 2인 플레이를 못 할 경우의 백업 | ⬜ 제출 전 촬영 |

**모바일 빌드(APK)는 만들지 않는다.** URP 기반 1인칭 공포 게임을 모바일 브라우저에서 돌리는 건 무리이고(8-1), 요건이 "웹 URL **또는** APK"이므로 웹 URL 하나로 충족된다.

### 심사자가 혼자여도 게임을 볼 수 있게

이 게임은 **최소 2명(귀신 1 + 퇴마사 1)이 있어야 아무것도 검증되지 않는다.** 심사자가 혼자 링크를 열면 로비에서 대기만 하다 끝날 수 있다. 요건에 멀티플레이 금지는 없으므로 게임 구조를 바꿀 이유는 없고, 대신 두 가지로 덮는다:

1. **탭 2개로 2인 접속하는 방법을 실행 안내에 명시한다.** 웹 빌드라 브라우저 탭을 하나 더 열면 그대로 2인 접속이 된다. 추가 개발이 없고, 심사자가 **직접 플레이**해볼 수 있는 유일한 방법이므로 이게 주 경로다.
2. **플레이 영상을 함께 제출한다.** 실제 대전이 어떻게 돌아가는지 보여주는 백업. 심사자가 직접 해보지 않아도 게임을 이해할 수 있다.

더미 NPC는 만들지 않는다 — 위 두 가지로 충분하고 개발 비용만 크다.

**최소 인원 제한을 두지 않기로 한 결정(9번)이 여기서도 유효하다.** 하한을 걸어두면 심사자가 2인 접속조차 못 하게 된다.

### 실행 방법

> ⬜ **배포 후 이 절을 채울 것.** 아래는 채워 넣을 항목의 틀이다.

**플레이 링크**: `(배포 후 URL 기입)`

**플레이 영상**: `(촬영 후 URL 기입)`

**설치**: 불필요. 브라우저에서 링크를 열면 바로 실행된다.

**권장 환경**
- 데스크톱 브라우저 (Chrome / Edge 최신 버전 권장)
- 모바일은 지원하지 않는다
- 최초 접속 시 리소스 다운로드로 시간이 걸릴 수 있다

**혼자서 플레이를 확인하는 방법**
1. 링크를 연 뒤 방을 만든다 (방장 = 귀신 또는 퇴마사)
2. **같은 링크를 새 탭에서 한 번 더 연다**
3. 두 번째 탭에서 방 코드로 참가한다
4. 두 탭을 오가며 양쪽 진영을 모두 조작할 수 있다

**주의**: 소리는 브라우저 정책상 **화면을 한 번 클릭한 뒤부터** 재생된다 (6-3).

## 1. 기술 스택

| 항목 | 결정 | 비고 |
|---|---|---|
| Unity | **6000.5.4f1** | 버전 고정. 임의 업그레이드 금지 |
| 렌더 파이프라인 | **URP 17.5.0** | WebGL 대상이므로 경량 세팅 필요 (8번 참고) |
| 빌드 타겟 | **WebGL (Unity Web)** | 링크 하나로 브라우저에서 바로 플레이 |
| 네트워킹 | **Netcode for GameObjects (NGO)** | 서버 권한 모델. 오브젝트 가시성 제어가 이 게임의 핵심 |
| 접속 중계 | **UGS Relay** | 브라우저가 호스트가 될 수 있게 해주는 유일한 방법 |
| 방 생성/참가 | **UGS Lobby** | 방 목록·참가 코드 |
| 음성 채팅 | ⬜ **미정** | 시나리오 3-7 개정으로 텍스트 채팅이 음성으로 바뀌었다 (5-7) |
| 입력 | **New Input System** | `Assets/InputSystem_Actions.inputactions` |
| 캐릭터 이동 | **CharacterController** | 물리 시뮬레이션 없이 입력 그대로 이동 |
| 카메라 | **1인칭** | 시야 제한 = 공포감. 은신/탐지 로직도 단순해짐 |

전부 이 규모에서는 **무료**다. NGO·Unity Transport·Multiplayer Play Mode는 사용량 제한 자체가 없고, Relay는 월평균 동시접속 50명, Lobby는 지역군당 월 10 GiB까지 무료다. **한 방이 최대 5명**(시나리오 6번)이므로 Relay 무료 한도에 닿으려면 10개 방이 24시간 쉬지 않고 돌아가야 한다.

⚠️ **음성 솔루션은 아직 정하지 않았고, 무료 여부도 확인되지 않았다.** 원래는 채팅을 텍스트로만 하기로 하면서 Vivox를 스택에서 뺐었다 — "유료 전환 지점이 하나 줄고 WebGL 호환성 확인도 불필요해진다"는 게 근거였다. **시나리오 3-7이 음성으로 개정되면서 그 두 가지가 되살아났다.** 솔루션을 고를 때 5-7의 확인 항목을 먼저 볼 것.

### WebGL의 제약 (선택과 무관하게 적용)
- **브라우저는 리스닝 소켓을 못 연다** → WebGL 빌드는 원래 서버가 될 수 없다. **Relay가 유일한 예외**로, 브라우저가 Relay에 클라이언트로 붙으면서 기능적으로 서버 역할을 한다.
- **UDP를 못 쓴다** → WebSocket(TCP) 전용. TCP는 head-of-line blocking이 있어 패킷 유실 시 뒤가 밀린다. 이 게임은 저택을 걸어다니는 게임이라 치명적이지 않지만, 빠른 반응이 필요한 기능을 넣을 땐 감안할 것.
- **C# 멀티스레딩 불가.** 게임 로직·물리·네트워크가 전부 메인 스레드 한 줄에서 돈다. 멀티스레딩은 C/C++ 레벨에서만 지원된다.
- WSS가 필수이며 **자체 서명 인증서는 거부된다.** 정식 인증서가 필요하다 (8-2).

## 2. 네트워킹 아키텍처

이 게임은 **은닉 정보 게임**이다. 재미의 전부가 두 가지 비밀에 걸려 있다:

1. **귀신 본체·영혼의 위치** (시나리오 2번 — 둘 다 투명)
2. **약점 도구 3종이 무엇인지** (시나리오 3-1)

그래서 네트워킹에서 가장 중요한 요구사항은 성능도 편의성도 아니고 **"특정 클라이언트에게 특정 데이터를 안 보낼 수 있는가"** 다. NGO를 택한 이유가 이것이다.

> **원칙: "화면에 안 그리기"는 해결책이 아니다.** 데이터가 클라이언트에 도착한 순간 이미 뚫린 것이다. 렌더링을 끄는 게 아니라 **전송 자체를 막아야** 한다.

### 2-1. 서버 권한 모델

- NGO는 **client-server** 구조다. 서버가 진실의 원천이고, 클라이언트는 요청만 한다.
- Relay를 쓰면 **호스트 = 플레이어 중 1명의 브라우저**이며, 호스트는 서버와 클라이언트를 겸한다.
- NGO 2.x에는 distributed authority 모드도 있지만 **쓰지 않는다.** 권한이 분산되면 비밀을 독점할 주체가 사라진다. 반드시 client-server(호스트) 모드로 갈 것.
- 모든 판정 — 탐지 성공 여부, 제단 정답 여부, 공포스킬 사거리 — 은 **서버가 한다.** 클라이언트는 "이거 썼다"고 보고할 뿐 결과를 스스로 정하지 않는다.

### 2-2. 정보를 숨기는 세 가지 도구

| 도구 | 하는 일 | 이 게임에서의 용도 |
|---|---|---|
| `NetworkObject.NetworkHide(clientId)` | 해당 클라이언트에서 오브젝트를 **디스폰시키고 업데이트 전송을 끊는다** | 귀신 본체·영혼을 퇴마사 클라이언트에서 아예 없애기 |
| `NetworkVariable<T>` + `ReadPermission.Owner` | **소유자와 서버만** 읽을 수 있는 변수 | 약점 3종을 귀신에게만 전달 |
| `RpcTarget.Single(clientId)` | **특정 1명에게만** 실제로 전송 (`Group`, `Not`도 있음) | 탐지 결과를 사용한 본인에게만 |

`NetworkHide`가 특히 중요하다. 숨겨진 오브젝트는 그 클라이언트에서 **존재 자체가 사라지므로**, 개발자도구로 뒤져도 없는 데이터는 볼 수 없다. 덤으로 대역폭도 절약된다 — 보안 기능이자 최적화다.

### 2-3. 동기화 대상 분류

| 데이터 | 방식 | 비고 |
|---|---|---|
| 방 설정·밸런스 파라미터 | `NetworkVariable` (전체 공개) | 전원이 알아야 함 |
| 현재 게임 단계, 남은 시간 | `NetworkVariable` (서버 쓰기) | 전원 동기화 |
| 퇴마사 위치·회전 | `NetworkTransform` | 서로 보여야 함 |
| 퇴마사 생존 여부 | `NetworkVariable` (전체 공개) | 공개 정보. **흡수 여부는 더 이상 추적하지 않는다**(게이지로 대체) |
| 제단에 헌납된 도구 목록 | `NetworkList` (전체 공개) | 시나리오 3-3, 전원 공개 |
| 누가 귀신인지 (역할) | `NetworkVariable` (전체 공개) | 시나리오 2번 — 정체는 안 숨김 |
| 맵의 도구 배치 | 서버가 시드 생성 후 동기화 | 전원 동일해야 함 |
| **귀신 본체 위치** | `NetworkTransform` + **퇴마사에게 `NetworkHide`** | 서버와 귀신만 안다 |
| **귀신 영혼 위치** | 위와 동일 | 서버와 귀신만 안다 |
| **약점 도구 3종** | `NetworkVariable` + **`ReadPermission.Owner`** | 서버가 생성, 귀신만 읽음 |
| 귀신 현실화 후 위치 | `Hunt` 진입 시 **`NetworkShow`** | 사냥 단계에선 보여야 함 |
| 현실화 게이지 | `NetworkVariable` (전체 공개) | 위치 정보가 없어 공개해도 안전 |
| 음성 채널 | 솔루션 미정 (5-7) | ⚠️ **귀신은 발화 차단** — 소리가 곧 위치다 |

**약점 3종은 서버가 게임 시작 시 생성**하고, 귀신의 `NetworkObject`에 `ReadPermission.Owner`인 변수로 담는다. 퇴마사 클라이언트에는 전송되지 않는다.

### 2-4. 탐지 흐름 (서버 권한)

```
퇴마사 A가 위치 P에서 도구 X 사용
    │
    ▼
[Rpc(SendTo.Server)] UseToolRpc(도구=X, 위치=P)
    │
    ▼
서버가 판정 (서버는 귀신 위치와 약점을 모두 안다):
    귀신 본체가 P의 반경 R 안에 있는가?  AND  X가 약점 3종에 포함되는가?
    │
    ├── 예 → RpcTarget.Single(A) 로 "탐지 성공" 전송
    │         → 페널티 발동 (5-5). **게이지는 유지된다**
    │
    └── 아니오 → RpcTarget.Single(A) 로 "반응 없음" 전송
```

**성공과 실패 모두 응답을 보낸다는 점이 중요하다.** 실패 시 응답을 생략하면 통신 유무 자체가 단서가 된다. 두 응답의 크기·타이밍·연출 시간을 동일하게 맞춰야 시나리오 3-2의 모호성이 지켜진다.

이 판정이 서버에서 일어나므로 **귀신이 결과를 조작할 수 없다.** 제단 정답 판정, 공포스킬 사거리 판정도 전부 같은 구조다.

### 2-5. 남는 구멍: 호스트는 플레이어다

Relay를 써도 **호스트는 플레이어 중 한 명의 브라우저**다. 호스트 = 서버이므로 모든 비밀을 메모리에 갖고 있다. **호스트가 퇴마사라면 이론상 귀신 위치와 약점을 볼 수 있다.**

다만 현실적인 위험도는 낮다:

- 전원이 볼 수 있던 게 **1명으로 줄었다.**
- 난이도가 완전히 다르다. 브라우저 개발자도구로 JS 객체를 읽는 것과, **WASM 힙을 뒤지거나 빌드를 패치하는 것**은 요구되는 기술 수준이 다르다.
- 친구들끼리 하는 단계에서는 무시해도 된다.

완전히 없애려면 **전용 서버**가 필요하다 (Multiplay Hosting은 유료, 또는 VPS에 헤드리스 리눅스 빌드를 직접 운영). 지금 단계에서는 하지 않는다. 나중에 필요해지면 게임 로직은 그대로 두고 호스팅 방식만 바꾸면 되므로, **서버에서 실행될 코드와 클라이언트 코드를 섞지 않는 것**만 지키면 된다.

### 2-6. NGO 버전 주의 (⚠️ 자주 틀리는 지점)

**NGO 2.x부터 RPC 문법이 통합됐다.**

```csharp
// NGO 2.x — 이걸 쓴다
[Rpc(SendTo.Server)]        void UseToolRpc(...) { }
[Rpc(SendTo.SpecifiedInParams)] void ResultRpc(..., RpcParams p) { }

// NGO 1.x — 인터넷 예제 대부분이 이 문법. 쓰지 말 것
[ServerRpc] void UseToolServerRpc(...) { }
[ClientRpc] void ResultClientRpc(...) { }
```

Unity 6 프로젝트이므로 **NGO 2.x 기준**으로 작성한다. 검색으로 나오는 튜토리얼·블로그는 상당수가 1.x 시절이라 그대로 복사하면 컴파일되지 않거나 동작이 다르다. 참고 코드를 가져올 땐 NGO 버전을 먼저 확인할 것.

## 3. 게임 상태 머신

시나리오 4번의 흐름도를 그대로 상태로 옮긴다. **서버만 상태를 전이시키고**, 클라이언트는 `NetworkVariable`을 구독해 반응한다.

```
Lobby ──▶ Hiding ──▶ Investigation ──┬──▶ Result ──▶ Lobby
          (30초)      (제한시간)      │
                                      └──▶ Hunt (60초) ──▶ Result
```

| 상태 | 진입 조건 | 종료 조건 | 주요 처리 |
|---|---|---|---|
| `Lobby` | 방 생성 / 게임 종료 후 복귀 | 방장이 시작 | 밸런스 설정, 역할 배정 |
| `Hiding` | 게임 시작 | 은신 시간 종료 (기본 30초) | 귀신 은신처 선택, 퇴마사 대기지점 고정 |
| `Investigation` | 은신 종료 | 제단 정답 / **게이지 100%** / 시간 종료 | 메인 게임. 본체 이동 불가 |
| `Hunt` | **게이지 100%** or 제한시간 종료 | 60초 경과 or 퇴마사 전멸 | 귀신 현실화, 이동속도 2배 |
| `Result` | 승패 확정 | 표시 후 복귀 | 승패 표시, 약점 공개 |

**역할 배정**: 서버가 `Lobby` → `Hiding` 전이 시점에 무작위로 귀신 1명을 정해 **공개 `NetworkVariable`** 에 기록한다. 시나리오 2번에 따라 누가 귀신인지는 숨기지 않는다 — 숨기는 것은 정체가 아니라 위치이므로, 역할을 공개해도 게임이 성립한다.

같은 시점에 서버가 해야 할 일이 두 가지 더 있다:
1. **약점 3종 무작위 생성** → 귀신의 `ReadPermission.Owner` 변수에 기록 (2-3).
2. **귀신 본체·영혼 오브젝트를 모든 퇴마사 클라이언트에서 `NetworkHide`** (2-2).

`Hunt` 진입 시에는 반대로 `NetworkShow`를 호출해 귀신을 현실화한다. **이 두 호출이 이 게임 은닉 구조의 전부**이므로, 상태 전이 코드에서 빠뜨리지 않도록 주의할 것.

### 4-1. 액션맵 구성

현재 `InputSystem_Actions`는 Unity 템플릿 기본값이라 이 게임에 안 맞는 액션이 섞여 있다. 아래처럼 재편한다.

### 2-2-1. ⚠️ 귀신 투명 처리 — NetworkHide를 쓰지 않기로 했다

2-2는 `NetworkObject.NetworkHide`로 **데이터 자체를 안 보내는** 설계였다. 구현해보니 치명적인 예외가 있었다:

> **`NetworkHide`는 서버 자신에게 쓸 수 없다.** NGO가 예외를 던진다.

호스트가 곧 서버이므로 **호스트가 퇴마사로 배정되면 귀신이 그대로 보인다.** 서버는 탐지 판정·스킬 사거리를 계산해야 하니 귀신 위치를 반드시 알아야 하고, 그 서버를 사람이 돌리는 한 어떤 엔진을 써도 같다. (Playroom Kit은 per-client 가시성 제어가 아예 없어 더 나쁘다 — 전원에게 새어나간다.)

**결정: 렌더러 제어 방식(`Ghost/GhostVisibility.cs`)으로 간다.**

| | NetworkHide | 렌더러 제어 (채택) |
|---|---|---|
| 개발자도구 치팅 | 불가능 | **가능** |
| 호스트/클라이언트 동작 | 다름 (호스트에 구멍) | **동일** |
| 게임 화면상 은닉 | 됨 | **됨** |

사전과제라 **게임 화면에서 안 보이면 충분하다**는 판단이다. 대신 호스트/클라이언트 동작이 완전히 같아져 디버깅이 쉬워지고, 역할 무작위 배정을 유지할 수 있다.

**전용 서버(headless)를 도입하면 원래 설계로 되돌릴 수 있다.** 그때는 어떤 플레이어도 서버가 아니므로 `NetworkHide`가 전원에게 완전히 작동한다. WebGL 페이지가 HTTPS라 WSS가 필요한 점만 유의.

약점 3종(`ReadPermission.Owner`)과 탐지 결과(`RpcTarget.Single`)는 **그대로 유지된다** — 이 둘은 서버 예외가 없어 호스트에게도 정상 작동한다.

### 4-2-1. 현재 조작 (실측 기준)

| 키 | 퇴마사 | 귀신 |
|---|---|---|
| `WASD` / 마우스 | 이동 / 시점 | 이동 / 시점 |
| `Shift` | 달리기 (×1.6) | 달리기 (×2.0) |
| `Space` | 점프 | 점프 |
| **`F`** | **도구 줍기 · 문 여닫기 · 제단 헌납** | — (문은 통과) |
| 좌클릭 | 도구 사용 | — |
| `G` | 도구 버리기 | — |
| `Q` | — | 영혼 분리/복귀 |
| **`Ctrl`** | — | **조사=영혼 흡수 / 사냥=처형** |
| `Tab` 홀드 → 좌클릭 | 이모트 (3인칭) | 이모트 (사냥 단계만) |
| `` ` `` (백틱) | 메뉴 (설정 / 나가기) | 메뉴 (설정 / 나가기) |

메뉴 키만 액션맵을 쓰지 않고 키보드를 직접 읽는다 — 액션맵이 진영·상태에 따라 갈리는데
메뉴는 어느 상태에서든 열려야 하기 때문이다. **`ESC`는 쓸 수 없다**: 브라우저가 포인터 잠금
해제·전체화면 종료에 먼저 써버려 웹 빌드에서는 Unity까지 오지 않는다.

도구·문·제단은 `IInteractable` 하나로 묶여 있다 — 같은 키를 쓰는데 조준·프롬프트·실행 경로가 갈라지면 "왜 이건 되고 저건 안 되지"를 매번 따로 디버깅하게 된다.

**모든 상호작용은 누르는 즉시 실행된다.** 처음엔 도구 줍기에 홀드 게이지를 뒀으나 뺐다 — 도구가 30개나 흩어져 있어 매번 홀드하면 수집이 지루하고, 좌클릭으로 도구를 쓰는 감각과도 어긋난다. 설정값만 0으로 두면 코드에 잔재가 남으므로 **`HoldDuration` 개념 자체를 인터페이스에서 제거**했다.

**달리기 배수가 진영별로 다르다.** 시나리오 6번은 "영혼 = 퇴마사 속도"로 정했지만, 추격이 성립하려면 귀신이 더 빨라야 한다는 판단으로 영혼을 2배로 뒀다. 사냥 단계 귀신은 이미 2배라 배수를 적용하지 않는다 — 곱하면 퇴마사가 손쓸 수 없다.

**귀신은 문을 열지 않는다.** 시나리오 2번이 영혼의 문 통과를 허용한 이유가 "저절로 열리는 문이 곧 위치 노출"이므로, 열 수 있게 두면 설계가 무의미해진다. 귀신은 **항상 `Soul` 레이어**라 본체 상태에서도 문을 통과한다.

### 4-3-1. 로비/게임 시점 전환

`GameManager.IsGameplayActive`(= 단계가 `Lobby`도 `Result`도 아님) **하나로** 카메라·커서·이동·시점을 동시에 전환한다. 각 컴포넌트가 따로 판단하게 두면 "커서는 잠겼는데 UI는 떠 있어 버튼을 못 누르는" 상태가 생긴다 — 실제로 한 번 밟았다.

| 상태 | 화면 | 커서 | 이동·시점 |
|---|---|---|---|
| `Lobby` / `Result` | 씬 카메라 (`LobbyCamera`) | 보임·자유 | 잠김 |
| `Hiding` / `Investigation` / `Hunt` | 플레이어 1인칭 카메라 | 숨김·고정 | 동작 |

**커서는 `PlayerRoleSetup`만 건드린다.** 여러 컴포넌트가 `Cursor.lockState`를 만지면 서로 덮어써서 원인을 추적할 수 없게 된다. 카메라는 씬과 플레이어 것 중 **정확히 하나만** 켜져 있어야 하며, `LobbyCamera`가 `LateUpdate`에서 넘겨받아 한 프레임 깜빡임을 없앤다.

## 5. 시스템별 설계

### 5-1. 도구 시스템 (시나리오 3-1)
- 도구 6종을 `enum ToolType { Camera, Cross, Bible, HolyWater, Detector, Incense }`로 정의.
- 맵의 은닉 지점(서랍·수납장·탁자 아래)을 `ToolSpawnPoint` 컴포넌트로 미리 배치. **스폰 지점은 도구 개수(30)보다 넉넉히** 깔아둬야 매 판 배치가 달라진다.
- 배치 결정은 **서버가 시드를 생성해 동기화** → 전 클라이언트가 같은 시드로 동일 배치를 재현. 배치 자체는 비밀이 아니므로(찾으면 되는 것) 이 방식으로 충분하다.
- 총 30개를 **종류당 5개씩 균등** 배치한다. 개수를 종류마다 다르게 하면 "이 도구가 유난히 많다 = 약점인가?" 같은 엉뚱한 추론이 생긴다.
- 소지 제한 1개는 `ExorcistInventory`에서 강제.
- 손에 들면 반경 표시(기본 3m): 바닥에 원형 데칼 또는 반투명 실린더. **로컬 표시만** — 네트워크 동기화 불필요.
- 사용 시 소멸.

### 5-2. 탐지 시스템 (시나리오 3-2)
2-4의 흐름 그대로. 구현 주의점:
- 반경 판정은 **수평 거리** 기준으로 할지 3D 거리로 할지 정해야 한다. 저택이 다층이면 위층에서 쓴 도구가 아래층 귀신을 잡는 문제가 생긴다 → **3D 거리 권장**.
- **결과는 `RpcTarget.Single()`로 사용한 본인에게만** 보낸다. 다른 클라이언트에는 전송 자체가 일어나지 않는다.
- **성공과 실패의 연출 시간을 반드시 동일하게** 맞출 것. 실패가 눈에 띄게 빠르면 연출 속도 자체가 단서가 되어 시나리오 3-2의 모호성이 깨진다.
- 도구 사용은 반드시 **서버가 검증**한다. 클라이언트가 "나 도구 썼다"고 보고할 때 실제로 그 도구를 소지했는지, 쿨다운·게임 단계가 맞는지 서버에서 확인할 것.

### 5-3. 제단 시스템 (시나리오 3-3)
- 헌납 목록은 `NetworkList`로 전체 공개. 서로 다른 3종이 모이면 판정 트리거.
- **판정은 서버**가 자신이 생성한 약점 3종과 대조해서 한다.
- 오답 시 서버가 생존 퇴마사 중 1명을 무작위 선정해 사망 처리 후 제단 초기화.
- 정답 시 퇴마사 승리 → `Result` 전이.

### 5-4. 공포스킬 / 영혼 흡수 (시나리오 3-4)
- 영혼 상태에서만 사용. 1회 1명. 쿨타임은 밸런스 파라미터, **사거리는 고정 상수**(초기값 1.5m).
- **밀착 사거리 = 어몽어스의 칼.** 대상 바로 옆에 붙었을 때만 발동한다. 이 짧은 사거리가 곧 이 게임의 난이도 조절 장치이므로, 로비에서 조절 가능하게 만들지 않는다.
- **UI: 사거리 안에 대상이 들어왔을 때만 스킬 버튼이 활성화**된다. 비활성 상태에선 눌리지 않는다 — 귀신 입장에선 "지금 찌를 수 있다"가 명확해야 하고, 이게 곧 접근 성공 피드백이 된다.
- **판정은 서버**가 수행한다. 클라이언트는 "스킬 쓰겠다"고 요청만 하고, 사거리·시야·쿨타임은 전부 서버가 검증한다.
- **거리 판정만으로는 부족하다.** 사거리가 짧아도 얇은 벽·닫힌 문을 사이에 두고 밀착하는 상황은 여전히 생긴다(어몽어스의 벽 너머 킬 버그와 같은 상황). → **영혼에서 대상까지 레이캐스트를 쏴 막힘이 없을 때만 성공** 처리한다.
  - 레이캐스트 마스크에는 **벽·바닥에 더해 문도 포함**한다. 영혼이 문을 통과할 수는 있어도, 실제로 통과해서 같은 공간에 들어와야 흡수할 수 있게 하려는 것. 즉 **이동 마스크와 스킬 마스크가 다르다** — 나중에 버그로 오해하지 말 것 (5-5 참고).
  - 가구·소품은 제외한다. 책상 뒤에 있다고 실패하면 답답하다.
- 서버가 대상의 상태를 `흡수됨`으로 변경하고 결과를 동기화한다.
- **흡수당한 본인에게 공포 연출을 재생한다** (`RpcTarget.Single`). 다른 퇴마사에게는 보내지 않는다 — 남이 흡수당한 걸 실시간으로 알면 그 자체가 위치 정보가 된다.
- **흡수는 사망이 아니다.** 흡수당한 퇴마사는 조작·도구 사용·제단 헌납이 전부 그대로 가능하다. 관전으로 넘기거나 입력을 막지 말 것. `흡수됨`과 `사망`은 **별개의 플래그**로 관리한다.
- **현실화 조건은 "흡수되지 않은 생존 퇴마사가 0명"** 이다. 단순히 흡수 카운트와 총 인원을 비교하면 안 된다 — 제단 오답으로 누가 죽는 순간(5-3) 조건이 영영 달성 불가능해진다. 사망자는 분모에서 빼야 한다.
- **탐지당하면 영혼 수집이 초기화**된다 — 전원의 `흡수됨` 플래그를 되돌린다.

> 흡수 위치가 새더라도 큰 문제가 아니다. 흡수는 **영혼**이 밀착해야 하는데, 도구가 탐지하는 것은 **본체**이고 본체는 다른 곳에 고정돼 있다(5-5). 오히려 퇴마사가 흡수 지점으로 몰려가면 헛다리를 짚는 셈이다.

### 5-5. 귀신 본체 / 영혼 (시나리오 2, 3-5)
- 본체는 `Hiding` 종료 시 위치 고정(이동 불가). 단 페널티 중 재은신할 때만 이동 가능.
- **영혼도 벽·바닥을 통과할 수 없다** (시나리오 2번). 즉 영혼은 퇴마사와 동일하게 충돌 처리되는 이동체다 → `CharacterController` + 콜라이더를 그대로 재사용한다. [PlayerMovement.cs](../Assets/Scripts/Player/PlayerMovement.cs)를 공유할 수 있다. 이동속도는 퇴마사와 동일(고정 상수)로 시작한다.
- **단 문은 통과한다.** 문을 못 뚫으면 영혼이 문을 열어야 하고, 저절로 열리는 문이 곧 위치 노출이 된다.
- **투명 처리는 렌더러 제어(`GhostVisibility`)로 한다** — 2-2-1 참고. 원래는 `NetworkHide` 설계였으나 서버 자신에게는 쓸 수 없어 호스트가 퇴마사면 뚫렸다.
- 영혼은 다른 플레이어와도 충돌하면 안 된다. **서버에서** 퇴마사가 보이지 않는 벽에 부딪히는 일이 생기면 위치가 새기 때문이다.
- **본체 좌표는 자식 Transform이 아니라 `NetworkVariable`로 둔다.** 자식은 부모를 따라다니므로 영혼이 나가도 본체가 끌려가 분리가 성립하지 않는다.
- **복귀 순간이동은 소유자가 실행해야 한다.** 위치 동기화가 소유자 권한(`ClientNetworkTransform`)이라 서버가 옮기면 다음 프레임에 덮어써지고, 결과적으로 본체 좌표만 영혼 자리로 끌려온다.

**레이어 구성** — 위 세 규칙을 Physics 레이어 매트릭스로 옮기면:

| 레이어 | 영혼과 충돌? | 비고 |
|---|---|---|
| `Wall` / `Floor` | ✅ 충돌 | 통과 불가 |
| `Door` | ❌ 통과 | 위치 노출 방지 |
| `Character` (퇴마사·본체) | ❌ 통과 | 부딪힘으로 위치가 새는 것 방지 |
| `Prop` (가구·소품) | ✅ 충돌 | 지형과 동일 취급 |

> ⚠️ 공포스킬의 레이캐스트 마스크는 여기에 `Door`를 **포함**한다 (5-4). 이동은 문을 통과하지만 스킬은 문에 막히는 게 의도된 동작이다.

**페널티 시퀀스** (시나리오 3-5) — 전부 서버가 관리한다:

탐지 성공 → 영혼 강제 복귀 → 도구 무효화 타이머 시작 → 그동안 본체 이동 가능 → 타이머 종료 시 다시 고정.

도구 무효화 중에는 **서버가 탐지 판정을 무조건 실패로 반환**하면 된다 (2-4의 판정 단계에 조건 하나 추가).

### 5-6. 관전 시스템 (시나리오 3-6)
- **사망한** 퇴마사만 관전으로 전환된다. 흡수당한 것만으로는 전환되지 않는다 (5-4).
- 사망한 퇴마사는 **생존한 퇴마사 1명**을 따라간다. 자유 카메라가 아니다 — 자유롭게 날아다니면 맵을 훑어 정보를 얻을 수 있다.
- **카메라는 대상의 살짝 뒤 3인칭.** 대상의 1인칭 카메라를 그대로 쓰면 남의 시점 흔들림을 계속 봐야 해서 멀미가 난다.
  - 시작 수치: 대상 뒤 **2.5m**, 위 **1.5m**, 대상의 눈높이를 바라봄. 위치는 `Lerp`로 부드럽게 따라간다(즉시 스냅하면 여전히 멀미가 난다).
  - **벽에 파묻히지 않게** 대상→카메라 방향으로 레이캐스트해 충돌 지점 앞까지 거리를 좁힌다. 최소 거리 **0.5m**.
- **UI**: 화면 아래 중앙에 관전 중인 퇴마사 닉네임, 그 좌우에 화살표 버튼. 누르면 다음/이전 생존자로 순환.
- 관전 목록은 **생존한 퇴마사만**. 귀신은 목록에 넣지 않는다.
- 관전 중이던 대상이 사망하면 다음 생존자로 자동 전환. 생존자가 없으면 게임이 이미 끝난 상태다.
- **관전자에게도 귀신은 안 보인다.** `GhostVisibility`가 단계만 보고 판단하므로(2-2-1) 관전 화면에서도 사냥 단계 전까지는 렌더링되지 않는다. 다만 **데이터는 도달하므로** `NetworkHide` 시절과 달리 원리적 차단은 아니다 — 전용 서버를 도입하면 그때 복원된다.

### 5-7. 음성 채팅 (시나리오 3-7) — ⬜ 솔루션 미정

**텍스트 채팅은 없앴다.** 시나리오 3-7 개정으로 모든 대화가 음성이 됐다.

| 대상 | 규칙 |
|---|---|
| 생존 퇴마사 | **거리 감쇠 음성.** 가까울수록 크고 멀면 안 들린다 |
| 귀신 | **듣기만 가능. 발화 차단** |
| 사망자 | 사망자 전용 채널 + **관전 대상의 귀를 공유** |

⚠️ **귀신 마이크 차단이 이 절에서 가장 중요하다.** 거리 기반 음성에서 귀신이 소리를 내면 방향과 거리가 그대로 드러나 **투명 처리(2-2-1)가 통째로 무의미해진다.** 대신 엿듣기는 허용해 정찰 수단으로 삼는다.

**솔루션을 고르기 전에 확인할 것:**

1. **WebGL에서 마이크·오디오가 실제로 동작하는가** — 브라우저 권한 요청 흐름 포함
2. **무료 한도가 제출 요건을 만족하는가** — 심사자가 유료 라이선스 없이 실행해야 한다
3. **3D 음성의 리스너 위치를 코드로 옮길 수 있는가** — 아래 이유로 필수다
4. 심사 기간 동안 서비스가 살아 있는가 (Relay와 같은 리스크, 8-2)

**3번이 관건이다.** 사망자는 자기 몸이 아니라 **관전 대상의 좌표**에서 소리를 들어야 한다. 리스너 위치를 제어할 수 없는 솔루션이면 이 요구사항을 포기해야 하므로, **기능을 만들기 전에 이것부터 검증할 것.**

> 이 설계는 시나리오 3-2("탐지 결과는 본인만 안다")와 짝을 이룬다. 거리 감쇠가 있으므로 **알아낸 것을 전하려면 위험을 무릅쓰고 가까이 가야 한다.** 정보가 정확·즉시 전달되지 않는 것이 의도다.

## 6. 연출 (애니메이션 · 사운드)

> **핵심 원칙: 연출의 수신 대상 = 정보 공개 범위.**
> 연출은 서버가 트리거하고 클라이언트가 재생하는데, **누구에게 보내느냐가 곧 정보 설계**다. 화려함보다 "이 소리가 누구에게 들리는가"를 먼저 정할 것. 2번의 은닉 정보 모델을 여기서도 그대로 따른다.

### 6-1. 소리는 이 게임에서 정보다

투명한 귀신을 찾는 게임이므로 **소리가 곧 위치 정보**다. 무심코 붙인 효과음 하나가 은닉 설계를 통째로 무너뜨릴 수 있다.

| 소리 | 누가 듣는가 | 이유 |
|---|---|---|
| 퇴마사 발소리 | **전원 (귀신 포함)** | 귀신이 퇴마사를 찾는 주요 단서. 사냥 단계 긴장의 핵심 |
| **영혼 이동 소리** | **본인만** | 투명한데 소리가 나면 위치가 그대로 샌다 |
| 귀신 본체 | **무음** | 고정된 채 숨어 있다. 소리가 나면 은신이 무의미 |
| 도구 줍기·사용 | 근처 전원 | 공개 행동. 다른 퇴마사가 눈으로도 보는 사실 |
| 제단 헌납 | 전원 | 시나리오 3-3에 따라 UI로도 공개되는 정보 |

**⚠️ 영혼 소리는 직접 막아야 한다.** `NetworkHide` 설계였다면 퇴마사 클라이언트에 오브젝트 자체가 없어 `AudioSource`도 없었을 텐데, **렌더러 제어로 바꾸면서 그 자동 보호가 사라졌다**(2-2-1). 오브젝트는 존재하므로 소리를 안 끄면 **투명한 귀신의 발소리가 그대로 들려 위치가 샌다.**

사운드를 붙일 때 `GhostVisibility`와 같은 조건(사냥 단계 이전에는 재생 안 함)으로 `AudioSource`도 함께 제어할 것. **현실화 = 모습과 소리가 동시에 드러나는 것**이라 연출상으로도 맞다.

### 6-1-1. 캐릭터 애니메이션 (구현됨)

퇴마사는 Mixamo로 리깅해 Humanoid 리그를 쓴다. Animator 상태: `Move`(블렌드 트리) / `Jump` / `Pickup` / `Dying` → `Died` / `Emote0~2`.

**지켜야 할 규칙 세 가지** — 전부 한 번씩 어겨서 문제를 냈다:

1. **Root Motion은 끈다.** `CharacterController`로 직접 움직이는데 애니메이션이 위치까지 옮기면 서로 싸워 미끄러진다.
2. **속도는 입력이 아니라 실제 이동량으로 잰다.** 입력으로 재면 벽에 막혀 못 가는 동안에도 걷는 시늉을 한다.
3. **블렌드 임계값은 게임 속도가 아니라 클립의 보폭 속도에 맞춘다.** 걷기 클립은 약 1.4m/s로 만들어져 있는데 임계값을 게임 속도(4m/s)로 잡으면, 뛰는 속도로 움직이면서 걷는 동작이 나와 발이 뒤처진다.

**클립 길이는 코드에 적지 않고 Animator에서 읽는다.** 점프 클립만 1.9 → 0.83 → 1.4 → 0.6초로 네 번 바뀌었다. 배속도 마찬가지로 **체공 시간에서 계산**한다 — `AirTime = 2√(2h/g)`. 그래야 점프 높이를 바꿔도 자동으로 맞는다.

**사망은 `Dying`(1회) → `Died`(유지) 두 상태로 나눈다.** 한 상태로 두면 쓰러지는 동작이 반복되거나 마지막 프레임에서 어색하게 멈춘다. 대기방 복귀로 되살아나는 경로도 두 상태 모두에 넣어야 한다.

### 6-1-2. 이모트 (구현됨)

`Tab` 홀드로 휠을 열고 마우스 방향으로 고른 뒤 **좌클릭**으로 재생, `Tab`을 놓으면 취소. 재생 중에는 3인칭으로 전환된다.

- **선택 결과는 서버를 거쳐 전원에게 퍼진다.** 춤은 남이 봐야 의미가 있는데 로컬 재생이면 본인 눈에만 보인다.
- **휠이 열린 동안 시점 회전·이동을 막는다.** 마우스가 항목 선택에 쓰이는데 화면까지 돌면 고를 수 없다. 좌클릭이 도구 사용으로 새는 것도 막아야 한다.
- **3인칭은 카메라를 새로 만들지 않고 있는 카메라를 뒤로 뺀다.** 두 대가 켜지면 화면이 겹친다. 뒤가 벽이면 레이캐스트로 당긴다.
- **이모트 중에는 자기 몸을 다시 보이게 해야 한다.** 1인칭용으로 `LocalBody` 레이어에 넣어 걸러내고 있어서, 되돌리지 않으면 춤추는 자기 모습이 안 보인다.
- **귀신은 현실화(사냥) 이후에만** 쓸 수 있다. 그 전에는 남의 화면에 그려지지 않아 의미가 없다.

### 6-2. 상호작용별 연출

| 상호작용 | 애니메이션 | 사운드 | 재생 대상 |
|---|---|---|---|
| 이동 | 걷기 (1인칭은 카메라 흔들림) | 발소리 | 근처 전원 |
| 도구 줍기 (`F`) | 손 뻗기 (`Picking Up`) | 집는 소리 | 근처 전원 |
| 도구 버리기 (`G`) | 내려놓기 | 툭 떨어지는 소리 | 근처 전원 |
| 도구 사용 (좌클릭) | **도구별 고유 모션** | 도구별 고유 소리 | 근처 전원 |
| **탐지 성공** | 도구가 반응하는 이펙트 | 반응음 | ⚠️ **사용한 본인만** |
| **탐지 실패** | 반응 없음 이펙트 | 무반응음 | ⚠️ **사용한 본인만** |
| 제단 헌납 | 던져 넣기 | 제단 반응음 | 전원 |
| 제단 정답 | 승리 연출 | 승리음 | 전원 |

| 흡수 성공 | 성공 피드백 | 성공음 | 귀신만 |
| **귀신이 탐지당함** | 영혼이 본체로 끌려가는 연출 | 페널티음 | 귀신만 |
| 사망 | 화면 암전 → 관전 전환 | 사망음 | 본인 (사망 사실 자체는 전원) |

**⚠️ 표에서 가장 조심할 두 줄은 탐지 성공/실패다.** 둘의 **연출 길이를 반드시 동일하게** 맞춰야 한다. 실패가 눈에 띄게 빨리 끝나면 연출 속도 자체가 단서가 되어, 시나리오 3-2가 요구하는 "실패 이유를 구분할 수 없음"이 깨진다 (5-2).

그리고 **흡수 연출은 당한 본인에게만** 보낸다. 남이 흡수당한 걸 실시간으로 알면 그게 곧 귀신의 위치 제보가 된다 (5-4).

### 6-3. 구현 주의사항

- **연출이 게임 로직을 막지 않게 한다.** 서버 상태는 이미 바뀐 뒤이고 연출은 그 사실을 보여줄 뿐이다. 연출이 끝나야 다음 동작이 가능한 구조로 짜면 지연이 그대로 조작 불능 시간이 된다.
- **⚠️ 브라우저는 사용자 조작 전까지 오디오 재생을 차단한다.** 페이지를 열자마자 나오는 소리는 재생되지 않는다. 로비에 **"클릭해서 시작"** 단계를 반드시 두고, 그 클릭을 기점으로 오디오를 초기화할 것. WebGL 배포에서 자주 놓치는 지점이다.
- **1인칭 손·도구 뷰모델을 우선한다.** 3인칭 전신 애니메이션은 관전(5-6)과 사냥 단계에서만 보이므로 우선순위가 낮다. 초기에는 뷰모델만 있어도 게임이 성립한다.
- 오디오 압축 설정을 방치하면 빌드 용량이 커져 첫 로딩이 길어진다 (8-2).

## 8. WebGL 성능과 배포

### 8-1. 성능 제약

어두운 저택 + 1인칭 공포 = 실시간 조명·그림자를 쓰고 싶어지는데, WebGL에서 가장 비싼 부분이 정확히 그것이다. **프레임 드랍이 생긴다면 범인은 거의 확실히 렌더링이지 네트워킹이 아니다** — C# 코드가 단일 스레드로 도는 환경(1번)에서 조명·그림자가 메인 스레드를 잡아먹기 때문이다.

- **라이트맵 베이킹을 기본으로.** 저택은 정적 지오메트리이므로 간접광은 전부 베이크.
- 실시간 그림자는 **손전등/플레이어 주변 1~2개 라이트로 제한.** 그림자 해상도와 거리도 낮춘다.
- WebGL2는 컴퓨트 셰이더가 없다 → 이를 요구하는 URP 기능(일부 포스트프로세싱 등)은 사용 불가.
- 현재 `Assets/Settings/`에 PC/Mobile용 렌더 에셋이 있는데, **WebGL은 Mobile 쪽 세팅에 가깝다.** WebGL 전용 퀄리티 레벨을 따로 만들 것.
- **현실적으로 데스크톱 전용이다.** 링크로 접속하는 특성상 친구가 폰으로 열어볼 가능성이 높으므로, 안내 문구가 필요하다.

### 8-2. 배포

목표는 **링크 하나로 브라우저에서 바로 플레이**다. WebGL 빌드를 정적 호스팅에 올리면 된다.

| 호스팅 | 적합도 |
|---|---|
| **itch.io** | 게임 배포 전용이라 가장 무난. Unity WebGL 압축을 알아서 처리 |
| **Cloudflare Pages / Netlify / Vercel** | 무난. 헤더 설정 가능 |
| **GitHub Pages** | ⚠️ **파일 하나가 100MB를 넘으면 못 올린다.** 커스텀 헤더도 불가 |

**꼭 챙길 것:**

- **HTTPS + 정식 인증서 필수.** Relay가 WSS를 요구하고 **자체 서명 인증서는 거부**한다. 위 호스팅들은 전부 무료 플랜에서 정식 인증서를 제공한다.
- **압축 설정이 배포 1순위 삽질 포인트다.** Unity WebGL은 기본적으로 Brotli로 압축하는데, 서버가 `Content-Encoding` 헤더를 보내줘야 동작한다. GitHub Pages처럼 헤더를 못 건드리는 곳에 올리려면 빌드 설정에서 **Decompression Fallback을 켜야 한다** — 안 켜면 흰 화면만 뜨고 아무 에러도 안 나온다.
- **첫 로딩 시간이 곧 이탈률이다.** 저택·캐릭터·소품 텍스처가 쌓이면 빌드가 수십~수백 MB가 된다. 친구가 링크를 눌렀는데 30초 검은 화면이면 그대로 닫는다. 텍스처·오디오 압축은 성능 문제가 아니라 **접속률 문제**로 다뤄야 한다.
- **⚠️ 심사 기간 동안 UGS 서비스가 살아있어야 한다.** 정적 파일은 호스팅에 그대로 있어도, **Relay/Lobby가 비활성화되거나 무료 한도를 넘으면 방 생성부터 실패한다.** 링크는 열리는데 게임은 시작되지 않는 최악의 상황이 된다. 제출 전에 UGS 대시보드에서 서비스 활성 상태와 사용량을 확인하고, 심사 기간 중에도 한 번씩 링크를 직접 눌러 확인할 것 (제출 요건 절).

### 8-3. 링크로 방 입장

UGS Lobby에는 Playroom 같은 "링크 공유 입장"이 기본 제공되지 않으므로 직접 만든다. 어렵지 않다:

1. 방장이 방을 만들면 참가 코드가 나온다.
2. `https://.../game/?room=ABCD` 형태로 링크를 만들어 공유한다.
3. 접속한 클라이언트가 `Application.absoluteURL`로 현재 주소를 읽어 쿼리를 파싱하고, 코드가 있으면 자동 입장시킨다.

## 9. 플레이테스트 조정 대상

설계상 미결정 사항은 없다. 아래 수치는 **전부 임의로 정한 시작값**이며, 실제로 플레이해보고 조정한다.

**구현 시 이 값들을 코드에 흩뿌리지 말 것.** 밸런스 파라미터는 로비 설정으로, 고정 상수는 `ScriptableObject` 하나에 모아둔다. 튜닝할 때마다 코드를 뒤지게 되면 조정을 안 하게 된다.

| 값 | 시작값 | 조정 신호 |
|---|---|---|
| 귀신 은신 시간 | 30초 | 귀신이 자리를 못 잡고 쫓기듯 숨으면 늘린다 |
| 게임 총 제한시간 | 8분 | 매 판 시간 초과로만 끝나면 늘리거나 도구를 늘린다. 반대로 남아돌면 줄인다 |
| 공포스킬 쿨타임 | 30초 | 흡수가 너무 빨리 끝나면 늘린다 |
| 재은신(도구 무효화) 시간 | 15초 | 귀신이 탐지 후 도망칠 여유가 없으면 늘린다 |
| 도구 탐지 반경 | 3m | 탐지가 거의 안 터지면 늘린다. 이 값이 게임 난이도에 가장 직접적 |
| 퇴마사 이동속도 | 4 m/s | 저택이 넓게 느껴지면 올린다 |
| 영혼 이동속도 | 4 m/s | 귀신이 퇴마사를 따라잡지 못하면 올린다 |
| 사냥 시 귀신 속도 | 8 m/s | 시나리오상 퇴마사의 2배 고정. 비율을 유지하며 조정 |
| 공포스킬 사거리 | 1.5m | 밀착했는데 안 걸리면 올린다. 벽 너머로 걸리면 5-4의 레이캐스트를 의심 |
| 도구 총 개수 | 30개 (종류당 5개) | 도구가 떨어져 손 놓고 있으면 늘린다. 너무 쉽게 추리되면 줄인다 |
| 최대 인원 | 5명 (귀신 1 + 퇴마사 4) | 제단 오답 1명 사망이 팀에 얼마나 치명적인지로 판단 |
| 관전 카메라 | 뒤 2.5m / 위 1.5m / 최소 0.5m | 멀미 여부, 벽에 파묻히는지 |

**최소 인원은 두지 않는다.** 2명(귀신 1 + 퇴마사 1)으로도 시작할 수 있어야 개발 중 검증이 된다 — Multiplayer Play Mode로 2인을 띄워 확인하는 게 기본 개발 루프다 (10번). 실제로 인원이 적으면 재미가 없다는 게 확인되면 그때 하한을 넣는다.

## 10. 구현 순서 제안

**처음부터 NGO 서버 권한 구조로 짓는다.** 이 게임은 "무엇을 누구에게 안 보내느냐"가 곧 게임이라, 판정 로직을 일반 `MonoBehaviour`로 만들었다가 나중에 `NetworkBehaviour`로 옮기면 같은 걸 두 번 짜게 된다.

단 **Relay는 마지막에 붙인다.** 로컬 호스트로 먼저 완성하고, 인터넷 접속은 그 뒤다. Relay를 먼저 붙이면 "접속이 안 되는 건지 로직이 틀린 건지" 구분이 안 돼 디버깅이 지옥이 된다.

1. NGO 기본 골격 — `NetworkManager`, 접속(호스트/클라이언트), 플레이어 스폰
2. 1인칭 이동·시점 — 소유자만 조작, `NetworkTransform`으로 동기화
3. 역할 배정 + **은닉 정보 모델** (`NetworkHide` / `ReadPermission.Owner` / `RpcTarget.Single`)
4. 게임 상태 머신 + 타이머
5. 도구 줍기·소지·사용·반경 표시
6. 탐지 판정 (서버) + 제단 헌납·판정
7. 귀신 본체/영혼 전환, 공포스킬, 탐지 페널티
8. 관전·음성 채팅
9. 로비 UI·밸런스 설정
10. **Relay + Lobby 연동** — 인터넷 너머 접속, 참가 코드
11. WebGL 빌드·배포 (8-2) — 압축 설정에서 막힐 것을 감안해 일정을 잡을 것

> **배포는 마지막 단계가 아니라 제출 산출물 그 자체다** (제출 요건 절). 11번을 끝에 몰아두면 압축 설정·인증서·UGS 설정에서 막혔을 때 손쓸 시간이 없다. **초반에 한 번, 빈 씬이라도 좋으니 WebGL로 빌드해 실제 호스팅에 올려볼 것.** 배포 경로가 뚫려 있다는 걸 미리 확인해두면 마감 직전의 위험이 사라진다.

> **배포는 마지막 단계가 아니라 제출 산출물 그 자체다** (제출 요건 절). 11번을 끝에 몰아두면 압축 설정·인증서·UGS 설정에서 막혔을 때 손쓸 시간이 없다. **1~5단계 중 아무 때나 한 번, 빈 씬이라도 좋으니 WebGL로 빌드해 실제 호스팅에 올려볼 것.** 배포 경로가 뚫려 있다는 걸 미리 확인해두면 마감 직전의 위험이 사라진다.

**6~7단계는 반드시 로컬에서 끝내고 8단계로 갈 것.** Relay를 먼저 붙이면 "접속이 안 되는 건지 로직이 틀린 건지" 구분이 안 돼 디버깅이 지옥이 된다.

### 테스트 방법

**Multiplayer Play Mode**(`com.unity.multiplayer.playmode`)를 쓰면 에디터 하나에서 **가상 플레이어를 최대 3명**까지 띄울 수 있다(메인 포함 총 4명). 귀신 1 + 퇴마사 3까지 혼자 검증되므로 이 게임엔 충분하다.

이 게임은 귀신 1 + 퇴마사 1이 없으면 탐지·공포스킬·관전 중 무엇도 검증되지 않으므로, **1단계부터 이 기능이 필수다.** WebGL 빌드는 11단계 전까지 뜰 일이 없다.
